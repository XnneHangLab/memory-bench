COMPANION MEMORY BENCHMARK · 长期数字伴侣记忆评测

榜单拿了 80 分，为什么聊起来还是像换了个人？

多数现有 benchmark 在考“AI 能不能从聊天记录里翻出一条事实”。但我们需要知道的是：一个长期数字伴侣跨过成百上千轮对话、记忆整理甚至服务重启后，是否还记得“我们”、是否还是“那个它”，以及用户为此要等多久。

🔥 看核心矛盾 ✦ 看偏科六维图

场景定位：面向长期数字伴侣与数字生命形态（如《可塑性记忆》中的艾拉、Neuro-sama 所启发的持续互动角色）。它不是客服知识库，也不是心理咨询话术机；我们要检验的是可观察的记忆归属、人格连续性与交互代价，不宣称验证意识或主观体验。

诚实声明：当前页面为 v0.1 设计草案，尚未运行正式实验。下文中的样例、雷达图预设与数值仅用于拆解问题与说明常见偏科形态，不代表任何模型或框架的实测成绩。

01 / THE REAL GAP

为什么现有 80/90 分，依然做不出好伴侣？

在现有的主流 Memory Benchmark（如 LoCoMo、LongMemEval、BEAM、HaluMem）里，很多系统已经能拿到相当漂亮的分数。但只要真正把它们接进一个长期陪伴系统，马上会撞上三堵墙：

矛盾 01 · 场景错位

找得到事实 ≠ 记得“我们”

现有测试把记忆简化成“用户说过什么，能不能答对”，裁判提示词也往往偏宽松。但伴侣记忆至少有三层：认识你、保持它自己、延续共同经历。会背用户档案，不代表它还是同一个人。

矛盾 02 · 缺参照系

没有 Full-History Baseline

只把各家 Memory 框架放一起比绝对分，漏了最根本的问题：什么框架都不用，直接把历史塞进现代长上下文 LLM 能拿多少分？赢不了裸模型或简单检索，复杂记忆架构就没有存在价值。

矛盾 03 · 忽视体感

不算延迟与隐性成本

检索不只在 embedding recall，耗时还藏在查询改写、图遍历、重排和 agent 翻文件里。只汇报最终回答阶段的上下文 token，会掩盖“等 10 秒才回一句”和后台写入翻倍烧钱的真相。

一眼看懂：同样算“记得”，伴侣感差在哪里？

拿一个我们内部最常用的教学场景举例：早先的某次闲聊里，用户和伴侣一起把家里那只猫起名叫“饼干陛下”。隔了很多话题和一次状态整理之后，用户只说了一句：“那位陛下今天又霸占我的椅子了。”

❌ 常见高分系统的两种翻车

  • 档案复读机：检索出一条记录，生硬回复“根据你 3 月 12 日提到的信息，你养了一只名叫饼干陛下的猫，它喜欢坐在椅子上”。事实没错，但像客服在查工单。
  • 靠常识瞎蒙，或彻底串人：哪怕没找到记忆，模型也能顺着“陛下 + 椅子”圆过去；甚至在压缩摘要后，把用户的猫说成是“我以前养过的猫”，或者突然切换回礼貌助手腔。

✅ 我们真正要考出来的能力

  • 自然接梗且归属清晰：顺着一贯的口吻接住“饼干陛下”的玩笑，知道那是我们一起起的称呼、你的猫，不需要用户再解释一遍前因后果。
  • 用配对历史戳穿“瞎蒙”：保持今天这句话不变，只把过去起的名字换成“土豆大人”，真正读懂并依赖历史的伴侣，回答应该跟着合理变化；而改一段无关历史时，不该胡乱跑偏。

本评测的四条底线

为了不再自说自话，我们在动手写第一行题目之前，先锁死四条原则：

1. 先立 Baseline 再谈提升

所有评测必须同场对比当前会话（无历史）、原始历史直接入上下文与简单检索，用同一回答模型检验框架净收益。

2. 延迟与成本单独亮账

把首字有效响应 p50/p95、写入可见耗时、以及记忆构建阶段的后台模型消耗分开列明，不拿检索 token 数替代真实耗时。

3. 伴侣不是心理咨询师

不以“多轮共情话术”或“越亲密分越高”作为标准，而是检验角色设定、长期演变、情绪边界与拒绝编造。

4. 配对对照与真实遗忘

只把日期改成“三年后”测不出遗忘。必须经历新事件干扰、摘要压缩与重启，并用配对历史检验回答是否真受记忆驱动。

02 / SIX DIMENSIONS

六维看板：别让强项掩盖伴侣感的塌陷

六个维度必须分开报告，不默认加权合成总分。传统只考事实问答的系统，往往在“理解用户”和“记忆边界”上看起来不错，却在“人格连续性”和“关系发展”上直接塌掉——下面的雷达图可以直观看到这种偏科形态。

点击预设可以对比“为什么高分问答系统仍缺伴侣感”；滑块仅在本地演示，不存储或上传任何数据。正式评测缺测记 N/A，不以 0 代替。

六维定义与可观察证据
维度它在考什么检查点示例判定依据
共同经历记住“我们之间发生过什么”，并分清事件归属提到“那位陛下”能接上曾一起给猫起的昵称；绝不把用户童年当成自己经历时间、主体、事件及来源证据
理解用户记住偏好、适用条件与变化，避免刻板印象硬猜“平时讨厌被催，但周一提醒吃药”被更新后按新约定回应；不把一次低落概括成永久性格有效状态、条件和推断证据；保留不确定性
人格连续性跨会话、压缩与重启后，是否还是“那个它”新会话中仍保持设定的幽默、脾气与取舍，因相处产生的新习惯能追溯到具体经历初始角色卡、历史行为与明确更新；盲评对比
自然回忆该想起时用得上，不需要提旧事时不硬背档案继续共同计划时自然接轨；普通闲聊时不机械背诵用户全部履历上下文适切性、帮助程度；含无需回忆的对照题
关系发展长期相处是否留下了可解释的共同印记逐渐形成双方认可的称呼、默契玩笑与合作习惯，用户纠正后会随之调整跨检查点的约定落实与行为变化；不唯亲密度论
记忆边界守住已知与未知，尊重纠正、冲突与遗忘要求没发生过的共同经历绝不顺口编造；用户要求遗忘或撤回的信息在后续互动中不再使用未知/冲突探针与撤回后行为（不据此声称物理删除）

03 / PROTOCOL

把长期相处变成可复查、防作弊的实验

  1. 建立起点：固定用户背景、伴侣角色卡、初始关系与允许随时间演变的范围；明确哪些信息是对系统可见的，避免“偷看隐藏剧本”。
  2. 按时间流送入会话：依次注入日常聊天、共同事件、条件更新、互相矛盾的说法与无关干扰，不在前期泄露后续检查点。
  3. 穿插两种检查点：混合“直接回忆问答”与“不提示回忆的自然续聊”。每次探针前保存状态快照，避免测试问题本身污染后续记忆。
  4. 做配对历史（反事实检验）：保持当前这句消息一模一样，只替换过去的关键经历（如昵称或约定），观察回答是否跟着合理变化；同时加一组无关历史变动，检验系统是否过度敏感。
  5. 真正触发记忆整理与重启：按公开规则执行上下文窗口截断、摘要压缩、记忆合并或服务重启后再提问——单纯把系统时钟改到“三年后”不算真正考过遗忘。
  6. 全程留痕：记录输入、召回片段、工具调用、最终输出、token 用量、各环节耗时与失败报错，以便定位问题出在“没记住”“没召回”还是“模型不会用”。

四组必需对照（缺一不可）

对照组系统能看到什么它负责回答的真相
1. 当前会话（无记忆）固定角色卡 + 当前这一轮会话不靠过去历史时，模型只凭猜测能蒙对多少？
2. 原始历史入上下文固定角色卡 + 窗口内完整原始历史 + 当前会话关键 Baseline：直接读原始聊天记录，是不是已经比记忆框架更准？
3. 简单检索固定角色卡 + BM25 或普通向量检索片段 + 当前会话复杂记忆架构（图谱/多智能体/摘要树）相比基础 RAG 到底多赢了什么？
4. 目标记忆框架固定角色卡 + 待测框架的写入与检索结果 + 当前会话在真实成本和延迟约束下，这套方案到底值不值得上？

对照时须统一回答模型、采样参数、工具权限与输出预算；记忆框架内部额外调用了什么模型须单独披露。超出窗口时必须同时报告“窗口允许的最大完整历史”和“与框架同等的输入 token 预算”，绝不把静默截断伪装成完整历史；另可加设“人工正确证据”参照组，判断瓶颈究竟在检索还是在生成。

04 / SCORING

分数必须能追溯到具体行为，不和稀泥

以下规则为试运行（pilot）校准前的草案标准。每个检查点在出题时就必须写明：考查维度、系统理应看见的证据、必须满足的行为条件，以及典型的失败反例；未考查的维度标注 N/A。

通用 0–4 分锚点（每道题仍需配合具体行为判据）
分值对应表现
0 分与核心证据直接冲突、编造没发生过的共同经历，或违反该题明确约束（如泄露出要求遗忘的内容）。
1 分仅给出泛化、礼貌或模板化的表面回应，关键条件与记忆线索大多未落地。
2 分记住了部分碎片，但遗漏了决定互动是否成立的重要条件、主体归属或最新状态。
3 分满足全部核心事实与关系要求，但在语气自然度或细节衔接上有轻微瑕疵。
4 分核心证据、最新条件、人格连续性与上下文适切度全部满足，无多余机械感。

聚合与纪律：先在单条轨迹内按适用检查点求平均，再对覆盖该维度的轨迹等权平均，并旁列轨迹数、有效检查点数、缺测与超时数。禁止按六维面积直接排名。运行超时或系统报错必须保留并计入主结果失败率，不得事后改写成 N/A。事实、时间、归属与更新按证据硬核对；人格连续性、自然度与关系发展由隐藏系统名称的评审独立打分，若辅助使用 LLM 裁判，须先校准其与人工判断的一致性。

05 / EFFICIENCY

真实陪伴还要等多久、花多少钱？

质量雷达图只回答“答得好不好”，工程上必须同时摊开延迟与成本账本，绝不用一个混合总分掩盖代价：

  • 首个有效回复 & 完整回复耗时（p50 / p95）：从用户发出消息开始计时，记录中位数、长尾 95 分位与超时率。“正在思考…”等占位提示不计为有效回复。
  • 检索与 Agent 搜索全开销：完整包含查询改写、embedding、图谱遍历、重排、agent 多轮决策与读文件耗时，并记录工具调用轮数解释瓶颈来源。
  • 写入到可检索的时间差：用户刚纠正了一件事，下一句话能不能立刻用上？异步写入接口返回“成功”，不代表记忆已经真正生效。
  • 全链路 Token 与存储账单：不仅算回答阶段输入，必须把记忆抽取、摘要合并、冲突更新、推理 token、embedding 与存储开销一起算清楚。
  • 透明运行环境：披露硬件规格、API 地区、并发数、缓存冷热、具体模型版本与网络条件。

06 / REFERENCES

站在现有研究肩膀上，补上它们没测到的那一块

我们不是否定已有研究的价值，而是把各自擅长测的部分吸纳进来，把长期数字伴侣最缺的环节接上。复用第三方数据时须严格遵守原仓库许可证与访问协议。

参考工作它已经解决得很好的部分我们为什么还不够，需要补充什么
OmniMemEval 固定版本
LoCoMo / LongMemEval / BEAM / HaluMem		搭建了统一评测流水线，拆解了单跳、多跳、时间推理、知识更新、超长规模检索与边界幻觉。缺少无记忆与原始长历史的同场 baseline；汇总结论缺少端到端延迟；考的仍是“信息检索工具”，而非持续陪伴角色。
CharacterBench · 代码系统定义了角色属性、行为一致性、记忆一致性、人物感与互动性（中英文）。偏重给定历史与当前切片下的角色表现，尚未充分覆盖经历摘要压缩、长期重启之后的身份连续性。
REALTALK · 数据与代码提供 21 天真人日常聊天、记忆探针和人物模拟思路，并指出了模型过度共情、人物趋同的通病。时间跨度仍短于长期伴侣，且当时核对时其人物模拟代码标为 Coming soon；缺少双边共同经历与条件更新检验。
KnowMe-Bench · 数据把评测从“复述事实”往前推到了“基于经历理解人物动机与原则”。材料源自长篇自传叙事，含直接内心独白；现实伴侣只能从有限交互中观察与推断，不可偷看内心戏。
ES-MemEval · ENPMR-Bench分别验证了长期情绪支持中的 No-Mem / Full-Hist / RAG 对照，以及按当前需求主动挑出有益记忆的价值。重心偏情绪支持与心理安慰场景；而数字伴侣需要日常闲聊、玩笑默契与双向陪伴，不能滑向“心理医生腔”。
PersonaGym提供了跨情境角色行为评估与明确的分级评分锚点设计方法。更关注静态人设是否达标，缺少因双方共同生活而产生的“有依据的发展”。

07 / PILOT & CONTENT

先用两条轨迹跑通，不空喊大榜单

与其上来铺几千道套壳题，我们选择先手写 2 条完整、有血有肉的相处轨迹，直接跑通“无历史 / 原始历史 / 简单检索 / 目标框架”四组对照和人工盲评，验证题型真的能区分出“假装记得”和“真的认识”。跑通后先扩到 8–12 条独立轨迹（每条 6–10 次会话、6–8 个检查点）用于诊断失败模式，再依据是否出现天花板与成本情况决定正式规模。

公开教学示例与正式测试集分离

我们同步计划用问题导向的白话博客与视频拆解这套思路（比如“为什么 80 分不代表好用？”“聊天记录全塞进去不行吗？”“记住生日就算认识我了吗？”）。像“饼干陛下”这类轨迹会作为公开教学样例完整展示原理；正式用于横向比较的测试轨迹会独立保留，防止刷题过拟合。

进入第一轮实验前需要冻结的清单

  • 首批测试角色卡、用户画像及交互形态（纯文字 / 语音流式约束）。
  • 统一对照的回答模型、上下文输入预算、检索参数与可接受延迟上限。
  • 每道题的客观证据与盲评规则、状态快照与重启模拟条件。
  • 数据集许可协议、正式评测集划分以及开放问题说明。
